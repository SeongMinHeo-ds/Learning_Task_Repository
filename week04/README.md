# 4주차 웹으로 확인하는 LLM 입력·출력 흐름

**목표:** role→입력 직렬화→교육용 token→준비 응답→형식 확인을 따라가고 실제 JSON 파싱 결과와 관찰 로그를 남긴다.

수행 방식: **PC 웹 데모 + 작은 실제 계산**. 주 5일·하루 6시간, 총 30시간이다. 아래 순서와 기준 설정으로 먼저 완료하고 확장은 그다음에 한다.

[입력 자료](DATA.md) · [참고 링크](RESOURCES.md) · [완료 체크](CHECKLIST.md)

## 1. 시작 전 준비와 기준 설정

1. demo.html을 PC 브라우저에서 연다. 서버·API 키·모델 다운로드가 필요 없다. 웹 데모를 다시 구현할 필요도 없다.
2. 기준 질문 LQ02, 출력 예산 80, 비교 예산 8. 교육용 token은 Unicode 문자 단위이며 실제 LLM tokenizer와 다르다.
3. 응답은 미리 작성한 예시를 재생한다. 모델 추론·temperature 효과·실제 모델 token 수를 측정한 것으로 쓰지 않는다.
4. 단순 작업은 실제 수행한다: 문자열을 문자 단위로 나누기, role별 입력 문자열 구성, 예산에 따른 예시 출력 절단, JSON.parse/json.loads 파싱, 관찰 기록 JSON 저장.

웹 파일은 이 폴더의 **[demo.html](demo.html)**이다. PC에서 더블클릭하거나 브라우저의 파일 열기로 연다. 서버·설치·API 키 없이 작동한다. 화면에서 실험하고 내려받은 JSON을 결과 폴더에 모은다.

## 2. 기준 실행 흐름

```text
PC 브라우저에서 demo.html 열기 → LQ02 선택 → 예산 80 → 실행 → JSON 저장
```

입력 준비 → 일별 작업 → 결과 파일 생성 → 정상·실패 비교 → 보고서 순서로 진행한다.

## 3. 1일차 · L16 role·입력·교육용 token 관찰

### 1-1. 수행

demo.html에서 안내와 계산 범위를 읽고 기준 질문 LQ02를 고른다. 입력을 한 번 실행한다.

- **나와야 할 것:** L16 관찰 기록
- **확인 방법:** 준비된 응답 재생이며 신경망 모델 실행이 아님을 기록한다.

### 1-2. 수행

role별 메시지와 입력 문자열, 교육용 token 목록을 차례로 확인한다.

- **나와야 할 것:** role·입력 문자열·문자 개수 표
- **확인 방법:** system·user 정보가 합쳐지는 위치를 찾는다. Unicode 문자 수를 실제 모델 token 수라고 쓰지 않는다.

### 1-3. 수행

한국어·영어·공백이 다른 입력으로 바꾸어 분리 결과를 비교한다.

- **나와야 할 것:** token_observations.csv
- **확인 방법:** 문자 수와 교육용 token 수가 같은 이유, 실제 tokenizer에서는 다를 수 있는 이유를 설명한다.

## 4. 2일차 · L17 준비 응답과 출력 분리

### 2-1. 수행

LQ02를 예산 80으로 실행해 준비 응답의 전체와 실제 표시된 출력을 비교한다.

- **나와야 할 것:** llm_demo.json
- **확인 방법:** 기준 출력은 {"answer": 8}이며 파싱에 성공한다.

### 2-2. 수행

예산을 8로 낮추어 출력이 어디서 끊기는지 확인한다.

- **나와야 할 것:** 예산 변경 전후 결과
- **확인 방법:** JSON이 중간에 잘리면 파싱이 실패한다. 모델 품질 변화라고 해석하지 않는다.

### 2-3. 수행

모델이 실제로 필요한 부분과 이 데모가 대신 보여주는 부분을 나누어 적는다.

- **나와야 할 것:** llm_flow_notes.md
- **확인 방법:** tokenizer·가중치·다음 token 확률 계산은 미구현임을 설명한다.

## 5. 3일차 · L18 JSON 파싱을 직접 실행

### 3-1. 수행

정상 객체 {"answer":8}, 배열 필드 {"items":["사과","바나나"]}, trailing comma 오류 {"answer":8,}를 각각 파싱한다.

- **나와야 할 것:** json_parse_checks.csv
- **확인 방법:** 성공·성공·실패 순서인지 실제 파서로 확인한다.

### 3-2. 수행

파싱 성공 후 answer가 숫자인지, items가 배열인지 별도로 확인한다.

- **나와야 할 것:** 문법 검사와 필드 검사 비교
- **확인 방법:** JSON 문법 성공과 요청한 스키마 만족을 구분한다.

### 3-3. 수행

동일 질문에서 출력 예산만 바꾼 기록을 만든다.

- **나와야 할 것:** prompt_comparison.csv
- **확인 방법:** 한 번에 한 변수만 바꾸며 미실행 모델 설정에 가짜 성능·시간을 적지 않는다.

## 6. 4일차 · L19 빈 입력·긴 입력·로그 저장

### 4-1. 수행

입력을 비우고 실행한 뒤 정상 질문으로 복구한다.

- **나와야 할 것:** 실패·복구 관찰 기록
- **확인 방법:** 원인과 다음 행동이 화면에 표시되어야 한다.

### 4-2. 수행

반복 문자열로 500자를 넘기는 입력을 만들어 실행한다.

- **나와야 할 것:** 긴 입력 확인 기록
- **확인 방법:** 데모의 500자 입력 제한이 실제 LLM context 제한과 다름을 기록한다.

### 4-3. 수행

정상 결과에서 JSON 저장을 눌러 다운로드한다. 파일을 열고 provenance·설정·입력·출력을 확인한다.

- **나와야 할 것:** llm_demo.json
- **확인 방법:** model_executed=false, toy_tokenizer=true, 생성 시간·모델 token 필드는 미측정으로 남는다.

## 7. 5일차 · L20 10개 예시 질문 관찰과 한계 정리

### 5-1. 수행

입력 질문 10개를 기준 예산 80으로 확인하고 기대 동작과 실제 표시 결과를 기록한다.

- **나와야 할 것:** llm_observations.csv
- **확인 방법:** LQ09는 의도한 잘못된 JSON 예시다. 수작업 답안을 실제 모델 정확도로 집계하지 않는다.

### 5-2. 수행

잘린 출력·모르는 정보·잘못된 JSON의 차이를 설명한다.

- **나와야 할 것:** 실패 유형 세 가지 설명
- **확인 방법:** 어떤 실패가 입력·형식·근거의 문제인지 구분한다.

### 5-3. 수행

웹 로그와 직접 파싱한 결과를 묶어 제출한다.

- **나와야 할 것:** 주간 보고서와 파일 목록
- **확인 방법:** 실제 계산한 부분과 시뮬레이션한 부분을 각각 적는다.

## 8. 제출 파일과 확인 기준

| 파일 | 내용·필드 | 확인 기준 |
| --- | --- | --- |
| llm_demo.json | provenance, model_executed, messages, toy_tokens, output, parse | 기준 LQ02·예산 80과 실패 비교 |
| json_parse_checks.csv | case, parse_success, schema_success, error | 정상 두 건과 오류 한 건 |
| token_observations.csv / prompt_comparison.csv | 입력·문자 수·예산·표시 결과 | 같은 조건에서 결과 재현 가능 |
| llm_observations.csv / llm_flow_notes.md | 10개 관찰과 실제 모델에서 다른 점 | 모델 추론 성능이라고 표시하지 않음 |

## 9. 주간 완료와 막혔을 때

동작 단계를 설명하고 JSON 파싱을 실제 실행하며, 준비 응답과 실제 LLM 생성을 구분한다.

각 L 번호마다 코드 또는 웹 관찰, 실제 결과 파일, 짧은 설명을 연결한다. 결과 숫자가 다르면 입력 파일·분할 index·버전·설정부터 대조한다. 오류가 나면 입력, 기대 결과, 실제 메시지, 시도한 내용을 기록한다. 미실행·미측정·미채점은 그대로 표시한다.
