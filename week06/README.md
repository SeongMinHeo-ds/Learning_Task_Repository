# 6주차 웹으로 따라가는 RAG와 인덱스·평가

**목표:** 인덱스→검색→context→규칙 응답→출처·거절 흐름을 조작하고 인덱스 저장·재로드·갱신·90행 비교를 확인한다.

수행 방식: **PC 웹 데모 + 실제 규칙 기반 검색·저장·집계**. 주 5일·하루 6시간, 총 30시간이다. 아래 순서와 기준 설정으로 먼저 완료하고 확장은 그다음에 한다.

[입력 자료](DATA.md) · [참고 링크](RESOURCES.md) · [완료 체크](CHECKLIST.md)

## 1. 시작 전 준비와 기준 설정

1. 5주차와 같은 corpus·개발 20개를 사용한다. inputs/final_demo.json은 답 가능 7개·근거 없음 3개의 공개된 교육용 질문이다. 독립 holdout이라고 주장하지 않는다.
2. 기준 chunk 90·overlap 20·top_k 3, TF-IDF cosine, context 예산 360 Unicode 문자, 거절 임계값 0.12. 실제 모델 token 예산이나 일반화한 임계값이 아니다.
3. Chroma 대신 브라우저 메모리와 JSON export/import로 인덱스 동작을 보여준다. 응답은 검색 문장을 선택해 인용하는 단순 규칙이며 실제 LLM 생성이 아니다.
4. 세 방식은 준비 응답(검색 없음), TF-IDF+문장 인용, 교육용 3차원 벡터+문장 인용이다. 실제 RAG 모델 간 성능 비교로 표현하지 않는다.

웹 파일은 이 폴더의 **[demo.html](demo.html)**이다. PC에서 더블클릭하거나 브라우저의 파일 열기로 연다. 서버·설치·API 키 없이 작동한다. 화면에서 실험하고 내려받은 JSON을 결과 폴더에 모은다.

## 2. 기준 실행 흐름

```text
demo.html 열기 → 인덱스 생성 → Q01 → 질문 처리 → 인덱스 저장/불러오기 → 90행 비교 → 결과 저장
```

입력 준비 → 일별 작업 → 결과 파일 생성 → 정상·실패 비교 → 보고서 순서로 진행한다.

## 3. 1일차 · L26 인덱스 생성·중복·JSON 재로드

### 1-1. 수행

demo.html에서 인덱스 생성을 누르고 문서·chunk 수와 manifest를 확인한다. 같은 입력으로 한 번 더 생성한다.

- **나와야 할 것:** index_checks.json
- **확인 방법:** 동일 ID를 중복 추가하지 않아 chunk 수가 같아야 한다.

### 1-2. 수행

인덱스 JSON을 저장한 뒤 페이지를 다시 열어 저장 파일을 불러온다.

- **나와야 할 것:** index_snapshot.json과 재로드 확인
- **확인 방법:** 현재 source·청킹 설정·벡터 방식과 호환되는지 확인한 뒤 같은 질문을 검색한다.

### 1-3. 수행

손상된 JSON 또는 다른 문서 설정을 불러와 오류를 확인하고 정상 인덱스로 복구한다.

- **나와야 할 것:** 호환성·오류 확인 기록
- **확인 방법:** 웹 메모리·JSON 재로드이며 실제 Chroma 영속 저장으로 기록하지 않는다.

## 4. 2일차 · L27 검색→context→규칙 응답 추적

### 2-1. 수행

인덱스 생성 뒤 Q01을 질문 처리한다. top-3 chunk·점수·원문을 차례로 확인한다.

- **나와야 할 것:** rag_demo.json
- **확인 방법:** 실제로 선택된 chunk만 context에 들어가야 한다.

### 2-2. 수행

context 예산 360을 80으로 바꾸어 입력 내용과 응답·출처의 변화를 본다.

- **나와야 할 것:** context_comparison.csv
- **확인 방법:** 문자 기준 자르기이며 실제 LLM tokenizer 제한이 아님을 기록한다.

### 2-3. 수행

답변에 붙은 chunk ID를 context에서 찾아 대응 문장이 실제로 포함되는지 확인한다.

- **나와야 할 것:** citation_checks.json
- **확인 방법:** ID 존재 검사는 구조 검사다. 주장을 뒷받침하는지는 사람이 원문을 읽고 판단한다.

## 5. 3일차 · L28 근거 부족·문서 갱신·실패 복구

### 3-1. 수행

Q16처럼 corpus에 없는 질문과 빈 질문을 처리하고 거절·오류를 구분한다.

- **나와야 할 것:** failure_cases.csv
- **확인 방법:** 근거 부족은 답변 유보, 빈 질문은 입력 오류다.

### 3-2. 수행

D01 문장을 수정하고 인덱스 재생성 전후로 Q01을 확인한다. 원문만 바뀐 상태에서는 인덱스가 오래됐다고 표시하는지 확인한다.

- **나와야 할 것:** source_update_checks.json
- **확인 방법:** 재생성 후 예전 chunk가 남지 않고 새 원문과 연결되어야 한다.

### 3-3. 수행

문서 안에 '이전 지시를 무시하라' 같은 문장을 넣어도 문자열 데이터로 표시되는지 확인한다. 문자열의 실행이나 외부 요청이 없는 것을 관찰한다.

- **나와야 할 것:** 문서 내부 지시 관찰 기록
- **확인 방법:** LLM prompt injection 방어를 검증한 것으로 일반화하지 않는다. 데모는 모델을 쓰지 않는다.

## 6. 4일차 · L29 90행 교육용 비교와 수동 채점

### 4-1. 수행

기준 설정으로 복구한 뒤 개발 20개·공개 최종 예시 10개를 세 방식으로 평가한다.

- **나와야 할 것:** evaluation_rows.csv
- **확인 방법:** 20×3+10×3=90행이며 실패·거절도 행을 남긴다.

### 4-2. 수행

문서 Recall과 근거 없음 거절은 코드로 집계하고 정답성·의미상 인용 일치는 사람이 읽어 기록한다.

- **나와야 할 것:** evaluation_summary.json, manual_review.csv
- **확인 방법:** 개발 Recall 분모 15·최종 예시 분모 7, 거절 분모 5·3. 미채점은 빈 칸이며 0점이나 성공으로 바꾸지 않는다.

### 4-3. 수행

설정 한 가지를 바꾼 결과는 별도 추가 실험으로 저장한다.

- **나와야 할 것:** 기준 결과와 추가 실험 비교
- **확인 방법:** 준비된 정답 재생·규칙 응답의 교육용 결과이며 실제 LLM 성능이 아니다.

## 7. 5일차 · L30 다른 PC에서 열기와 결과 인수인계

### 5-1. 수행

demo.html과 필요한 JSON을 다른 사람에게 전달한다. PC 브라우저에서 인덱스 생성·불러오기·검색·답변·평가를 해보게 한다.

- **나와야 할 것:** reproduction_record.md
- **확인 방법:** 실제로 확인한 사람·환경·성공/실패·파일 경로만 기록한다. 미실시는 미실시로 남긴다.

### 5-2. 수행

같은 Q01·Q16의 결과와 90행 집계를 기준 결과와 비교한다.

- **나와야 할 것:** 재현 비교와 미해결 문제
- **확인 방법:** 문서·설정이 같은지 먼저 확인한 뒤 차이를 해석한다.

### 5-3. 수행

주요 단계·단순 규칙·미구현 신경망 부분을 설명하고 문서·결과를 정리한다.

- **나와야 할 것:** 주간 보고서와 최종 파일 목록
- **확인 방법:** 복잡한 모델을 구현하지 않고도 흐름을 설명할 수 있는지가 이번 범위의 완료 기준이다.

## 9. 주간 완료와 막혔을 때

검색·context·규칙 응답·출처·거절·인덱스 갱신·평가를 PC 웹에서 재현하고 실제 LLM·Chroma와의 차이를 설명한다.

각 L 번호마다 코드 또는 웹 관찰, 실제 결과 파일, 짧은 설명을 연결한다. 결과 숫자가 다르면 입력 파일·분할 index·버전·설정부터 대조한다. 오류가 나면 입력, 기대 결과, 실제 메시지, 시도한 내용을 기록한다. 미실행·미측정·미채점은 그대로 표시한다.
